# Summary

Add the first independently useful slice of a versioned host-side enclosure
feature emitter: an M3 heat-set-insert/socket-head boss built from ordinary
base-Fusion construction planes, sketches, extrudes, combines, and cuts. One invocation emits one
bounded standalone Fusion Python transaction. Fusion remains the only durable
CAD state; the host package validates intent and emits source but does not
search geometry, persist feature instances, or become a CAD kernel.

The emitted result is geometrically and parametrically useful but is not a
native Autodesk `BossFeature`. Native Design Extension features, private
command IDs, preview `CustomFeature`, whole-enclosure generation, a new
manifest section, and a new CLI command are outside this slice.

# Settled decisions

- Use a shipped, versioned feature recipe in the ordinary modeling lane. This
  is user-directed by the attached research; the rejected alternative is an
  installed Fusion add-in because it adds lifecycle and trust cost without
  improving the first geometry slice.
- Build the v1 boss entirely from base-Fusion public features. This is
  user-directed; the rejected alternative is depending on native
  `BossFeatures.add()` because base-account entitlement remains unproven.
- Keep all durable feature state in Fusion parameters, attributes, named
  objects, and the timeline. This is user-directed; the rejected alternative
  is adding feature instances to `fusion-project.json`, which would turn an
  ordinary modeling operation into a manifest-backed lane.
- Require explicit target and participant ownership. This is user-directed;
  the rejected alternative is nearest/intersected-body inference because it
  can mutate neighboring assembly bodies.

# High-level technical design

The host package adds a small `fusion_design.enclosure_features` package with
three layers:

1. Frozen typed contracts validate the recipe version, semantic parameter
   names, Fusion expressions, evidence classification, and explicit entity
   references without importing Fusion.
2. A deterministic boss emitter converts one validated request into one
   standalone Python transaction beginning with the existing
   `# Generated by fusion-design` marker.
3. The transaction resolves only the named target/component/placement inputs,
   creates namespaced user parameters and ordinary native features, stamps
   `fusion_parametric_design` attributes, groups the timeline range, calls
   `computeAll()`, and prints a small result payload. It never writes files,
   opens the network, spawns processes, scans for nearest geometry, or uses a
   manifest.

The first recipe supports a planar support face, one cylindrical boss, an
insert bore, a required socket-head seat, and optional four-way
ordinary-extrude gussets. Base fillets are deferred because v1 deliberately
does not search generated edge topology. Editing is parameter-expression replacement;
inspection reports managed identity/native health; deletion removes only
objects carrying the requested feature instance ID. Unsupported topology or
unrecognizable managed structure refuses rather than rebuilding broadly.

# Live acceptance boundary

Offline tests prove deterministic source and policy, not CAD correctness. The
smallest live acceptance uses a disposable saved parametric Fusion document on
a base account: create the planar M3 insert boss, confirm explicit target body
ownership and solid body count, edit the bore expression, Compute All, inspect
feature health, save/reopen, and confirm neighboring bodies are unchanged. If
the live Fusion surface is unavailable during delivery, the PR must state that
gate as pending rather than describing offline doubles as production proof.

# Risks and refusals

- Fusion API syntax can pass offline compilation but fail live; preserve raw
  Autodesk errors and keep the live gate distinct.
- Timeline/object identity can become unsafe after manual edits; refuse with
  `manual-edit-prevents-update` rather than choosing a nearby object.
- Insert dimensions are hardware/formulation/process-specific; refuse missing
  evidence and never infer mechanical performance.
- Oversized generated source is acceptable only under the existing shipped
  marker; the process-spawn gate remains unconditional.
