# Fleet Privilege Brokers Skill Change Specification

## Scope and ranking

These changes target the Agent Utilities delivery skills. They are specifications only; this retrospective does not modify the skills. Current Agent Utilities 0.5.5 already contains hash-aware validation, frozen seam contracts, native-gate classification, model substitution disclosure, and complexity checkpoints added after the historical 0.4.2 run began. The changes below avoid duplicating those provisions.

Ranking weights: wall-clock/rework 30%, reliability 30%, breadth 15%, implementation effort 10%, regression risk 10%, causal confidence 5%.

## Ranked changes

### SC-01 — Deployable runtime-artifact closure

- **Target files/sections:**
  - `plugins/agent-utilities/skills/goal-driven-delivery/SKILL.md` — `First-Pass Quality Rules` and kickoff cadence.
  - `plugins/agent-utilities/skills/task-orchestrator/SKILL.md` — frozen contract/readiness for release lanes.
  - `plugins/agent-utilities/skills/thermo-nuclear-review/SKILL.md` — breaking-functionality review.
- **Change:** Add a hard admission and review gate.
- **Problem/findings:** A green build was mistaken for a distributable Windows helper (F01); completion was overclaimed (F11).
- **Evidence:** Enrollment requires two RID bundles; CI performs only restore/test/build; no tracked or published binaries; thread turn `019fca79-cb61-74a1-8f56-42a24bb1365d`.
- **Exact instruction / pseudodiff:**

```diff
+ Runtime artifact closure: If the outcome adds or changes a compiled,
+ generated, signed, downloaded, or platform-specific runtime artifact,
+ establish its complete delivery path before implementation expands.
+ Record: source and reproducible producer command; supported target
+ architectures; authentication/signing owner; packaged or published path;
+ integrity-manifest entry; installed/enrolled destination; upgrade/rollback
+ owner; and the smallest runtime/install smoke check. A build output or CI
+ compilation is not a delivered artifact. If a required link has neither a
+ repository-owned implementation nor an explicitly owned external prerequisite,
+ block the lane before downstream code and fixtures expand.
```

- **Triggers:** New native helper, code generator output, signed payload, vendored runtime, migration bundle, model asset, wasm/binary, mobile extension, installer, or any consumer that expects gitignored/generated bytes.
- **Exclusions:** Pure source/library changes where the ordinary package already carries all runtime bytes; docs-only changes.
- **Model/orchestration implications:** Use a fast scout for artifact mapping; Sol High/Max adjudicates trust/signing gaps; one release owner owns the path.
- **Required artifact:** `runtime-artifacts` receipt with producer→package→consumer chain and hashes.
- **Guardrails:** Do not force binaries into Git; an authenticated repository-owned release/download pipeline is valid. Do not weaken signing or native checks.
- **Interactions/conflicts:** Runs before LFG/CE Work expansion; feeds Thermos and release coupling. It complements, not replaces, CI/native canaries.
- **Expected effect:** Saves 3–8 h in failed-path cases; small cost otherwise. Reliability improvement: high. Cost reduction: high when triggered.
- **Effort:** Medium. **Confidence:** High. **Overfitting risk:** Low.
- **Acceptance criteria:**
  1. A build-only gitignored binary expected by enrollment blocks before feature implementation.
  2. A source-only npm/Python package does not create a spurious gate.
  3. A signed GitHub Release artifact passes only when install/enrollment consumes that exact authenticated artifact.
- **Evaluation scenarios:** E2 complex parallel delivery; E5 failure/recovery; an ordinary source-only library control.

### SC-02 — Existing-plan objective admission

- **Target files/sections:** Goal Driven Delivery `Lane contract and verification cadence`; Task Orchestrator before `Direct the work`.
- **Change:** Add a focused requirement-closure comparison before mutable work from an existing plan.
- **Problem/findings:** The fleet objective and the plan’s explicit macOS no-root exclusion diverged (F02); local completion evidence did not cover terminal requirements (F11).
- **Evidence:** Plan lines 16, 30, 60, 751, 787; user macOS question in turn `48059da1-47b3-406e-8282-5b266deb09f7`.
- **Exact instruction / pseudodiff:**

```diff
+ Existing-plan admission: Before mutable work, compare the source objective,
+ explicit user constraints, settled decisions, terminal state, and platform or
+ deliverable scope against the plan's inclusions, exclusions, implementation
+ units, and acceptance criteria. Record a compact closure table. A plan that
+ omits or contradicts an objective-level platform, deliverable, security
+ boundary, or terminal requirement is not implementation-ready; return it for
+ focused repair while preserving valid plan content. Do not reopen details the
+ objective genuinely leaves unspecified.
```

- **Triggers:** Existing plan, handoff, imported checklist, stale issue plan, or resumed task.
- **Exclusions:** Exact user instruction to implement only a named plan slice; obvious tiny tasks without a plan.
- **Model/orchestration implications:** Fast model can build the table; Sol resolves genuine contradictions. No agent fan-out until admission passes.
- **Required artifact:** Requirement-closure table with `covered`, `excluded-and-accepted`, `contradiction`, `unknown`.
- **Guardrails:** Avoid turning admission into full replanning. Ask/stop only on outcome-changing mismatches.
- **Interactions/conflicts:** Explicit user scope wins; security boundaries cannot be silently widened. Works before route selection.
- **Expected effect:** 3–4.5 h saved in this run; reliability high; negligible model cost.
- **Effort:** Small. **Confidence:** High. **Overfitting risk:** Low.
- **Acceptance criteria:** A plan that says “macOS no root” against a privileged cross-platform outcome is stopped; a plan intentionally scoped to Linux only under a Linux-only objective proceeds.
- **Evaluation scenarios:** E2 complex parallel; E3 strong-model escalation.

### SC-03 — Critical-path lane manifest and bounded fan-in

- **Target files/sections:** Task Orchestrator decomposition, placement, monitoring, fan-in; Goal Driven Delivery concurrency policy.
- **Change:** Rewrite lane creation around dependency-weighted outputs and explicit lifecycle.
- **Problem/findings:** 84 unique subagent thread IDs, 701 activity events, 25 interruptions, repeated reviewer/hash reconciliation, and polling-heavy monitoring (F03, F09, F13); source IDs were weakly bound (F12).
- **Evidence:** App aggregates for thread `019fc56f-...`; 96 spawn calls, 1,459 `wait_agent` calls, 503 agent messages, and 257 agent-list calls in raw rollout evidence.
- **Exact instruction / pseudodiff:**

```diff
+ Before dispatching more than two lanes, record a compact DAG. Every lane must
+ name: unique output; downstream consumer; dependencies; exclusive mutable
+ paths; model/effort; first receipt; freeze condition; terminal stop; and
+ whether its output was consumed. Prefer the fewest lanes that shorten the
+ dependency-weighted critical path. Read-only scouts close after returning
+ their artifact. At fan-in, stop or release lanes whose output is consumed,
+ superseded, or no longer on the critical path. Do not keep slots busy merely
+ because they are available. Monitor milestones rather than narration:
+ orientation, first consumed artifact, blocker, freeze, and final. Prefer one
+ bounded wait across active lanes and suppress unchanged snapshots.
+
+ Bind every remote/thread lane to host, cwd, repository, branch/base/head,
+ objective digest, plan digest, and checkpoint. A thread ID alone is not a
+ resume or authority receipt.
```

- **Triggers:** Three or more potential lanes, cross-repository work, long-running tasks, remote tasks, or dependent stacks.
- **Exclusions:** Two independent bounded scouts; simple task (must avoid manifest ceremony).
- **Model/orchestration implications:** Sol owns DAG; fast models scout; Luna/Terra implement. Concurrency cap is demand-driven, not slot-driven.
- **Required artifact:** In-memory/task-local YAML/JSON DAG receipt; not necessarily committed.
- **Guardrails:** One canonical writer per shared file. No sensitive objective body in metadata; digest and secret-free summary suffice.
- **Interactions/conflicts:** Extends current frozen contract; does not invoke Task Orchestrator for simple single-lane work.
- **Expected effect:** 2–5 h and substantial token reduction on comparable complex runs; reliability medium-high.
- **Effort:** Medium. **Confidence:** Medium-high. **Overfitting risk:** Low.
- **Acceptance criteria:** Unused lanes are stopped at fan-in; a four-lane plan shows why each shortens the critical path; simple tasks stay single-lane.
- **Evaluation scenarios:** E1 anti-over-orchestration; E2 complex parallel; E5 recovery.

### SC-04 — Progress-budgeted model redirect

- **Target files/sections:** Task Orchestrator model routing; Goal Driven Delivery implementation carrier.
- **Change:** Add an output-based progress receipt and one bounded redirect.
- **Problem/findings:** Three Luna attempts reported at least 519k tokens and zero edits; one waited on unclosed stdin (F04, F08).
- **Evidence:** Turns `70728450-c152-41fc-a3b9-9c94db16b2df` and `647309cc-726e-4deb-9b5d-e32532819417`.
- **Exact instruction / pseudodiff:**

```diff
+ Give each implementation lane a progress budget appropriate to its risk.
+ Require an orientation receipt naming owned paths, reuse points, first check,
+ and next mutation within 5-10 minutes; require the first scoped artifact or
+ edit within 15-20 minutes for routine implementation. If the lane is still
+ rereading, waiting for stdin, or has no consumed output, diagnose once and
+ redirect once to the verified economical fallback or narrower task. Security
+ architecture may declare a longer receipt budget, but must still return a
+ decision artifact. Tokens alone do not determine progress or wall time.
```

- **Triggers:** Implementation/model-specific lane, especially preferred-provider routing.
- **Exclusions:** Explicit research-only work, long native build/test already making observable progress, user-mandated model with no fallback.
- **Model/orchestration implications:** Luna remains preferred; Terra fallback only under existing verified availability policy. Redirect does not change provider/transport authority.
- **Required artifact:** Progress receipt and redirect reason.
- **Guardrails:** Do not kill healthy long tests or deep security reasoning with a produced decision artifact.
- **Interactions/conflicts:** Works with current model disclosure and provider-task routing.
- **Expected effect:** 0.5–1 h wall time and very high token savings in this run; reliability neutral-to-positive.
- **Effort:** Small-medium. **Confidence:** High. **Overfitting risk:** Low.
- **Acceptance criteria:** A no-edit reread lane redirects once; a productive long analysis continues; no silent provider/model substitution occurs.
- **Evaluation scenarios:** E3 strong escalation; E4 fast-model majority; E5 hung process.

### SC-05 — Deterministic risky-review and simplification packet

- **Target files/sections:** `plugins/agent-utilities/skills/thermos/SKILL.md` workflow; code-quality and security reviewer prompts.
- **Change:** Add a risk manifest, not another reviewer.
- **Problem/findings:** Reviews found many local defects but missed a 5,100-line helper’s absent delivery path and did not enforce existing complexity thresholds; provider reviews stalled or reviewed moving inputs (F01, F03, F07, F11, F14).
- **Evidence:** Historical code-quality skill already treats >1,000 lines as presumptive complexity; final helper size/distribution surfaced only after user challenge.
- **Exact instruction / pseudodiff:**

```diff
+ For risky, release, cross-platform, or native-artifact diffs, the Thermos
+ packet must include: base/head and frozen content hashes; changed-file
+ pre/post line counts; every file crossing 1,000 lines; new runtime/build/
+ generated artifacts and their package/install consumers; public/security
+ boundary deltas; reused hash-bound test receipts; and unresolved native or
+ release gates. Each reviewer must disposition every threshold crossing and
+ artifact chain. A file crossing 1,000 lines requires an explicit
+ reuse/delete/split/justify disposition; "no simplification" without that
+ evidence is not a clean result. Run one correctness/security review and one code-quality
+ review in parallel. Add a cross-model review only for a distinct question
+ after provider/auth preflight; time-box no-output waits.
```

- **Triggers:** Risky/security/native/release/cross-platform work or >1,000-line changed file.
- **Exclusions:** Tiny/docs-only diffs.
- **Model/orchestration implications:** Independent Sol High/Max mandatory; optional cross-model review only when available and uniquely scoped.
- **Required artifact:** Deterministic review packet and dispositions.
- **Guardrails:** Preserve independent review; do not replace tests or native gates.
- **Interactions/conflicts:** Operationalizes existing adequate complexity rules; avoids duplicate full suites.
- **Expected effect:** 20–60 min less review wait and much higher architecture-defect detection.
- **Effort:** Medium. **Confidence:** High. **Overfitting risk:** Low.
- **Acceptance criteria:** Review flags a new 5k-line helper with no package path; two reviewers do not both rerun the same full suite; stalled optional provider review cannot block indefinitely.
- **Evaluation scenarios:** E2 complex; E3 strong escalation; E5 provider unavailable.

### SC-06 — Governing-skill provenance and restart receipt

- **Target files/sections:** Goal Driven Delivery kickoff/evidence; Task Orchestrator readiness and handoff.
- **Change:** Add procedural provenance to the task manifest.
- **Problem/findings:** Run started under 0.4.2, observed 0.5.2 after restart, and referenced a removed 0.4.1 cache path; 30 compactions and multiple restarts required narrative reconciliation (F09, F12).
- **Evidence:** Historical Git reconstruction and app turn boundaries.
- **Exact instruction / pseudodiff:**

```diff
+ At kickoff record each governing workflow skill's resolved source path,
+ version, and content digest. Before resume after restart, compaction handoff,
+ or plugin refresh, compare the receipt. Preserve the accepted objective,
+ authorization, and terminal contract; apply newer safety requirements
+ immediately, but do not silently change carrier, model, test, shipping, or
+ review policy. Record the procedural delta and the chosen reconciliation.
+ Also checkpoint lane hashes, consumed outputs, blockers, and next commands.
```

- **Triggers:** Long-running, remote, delegated, or restart-resumable task.
- **Exclusions:** Tiny single-turn task.
- **Model/orchestration implications:** Fast read-only check; Sol adjudicates conflicting procedural deltas.
- **Required artifact:** Skill provenance plus restart receipt.
- **Guardrails:** Never execute from an obsolete cache solely to preserve history; use historical content for audit and current safety rules for execution.
- **Interactions/conflicts:** Complements provider identity/handoff receipts.
- **Expected effect:** 0.5–2 h context/recovery savings on long runs; reliability high.
- **Effort:** Medium. **Confidence:** Medium-high. **Overfitting risk:** Low.
- **Acceptance criteria:** Restart detects skill version change and records reconciliation; unchanged restart resumes from next command without broad reread.
- **Evaluation scenarios:** E5 restart/recovery.

### SC-07 — Objective-delta and dependency-invalidation gate

- **Target files/sections:** Goal Driven Delivery re-evaluation after later instruction; Task Orchestrator `Direct the work`; current hash-based cadence contract tests.
- **Change:** Add a compact impact slice for late scope and a concrete shared-contract trigger.
- **Problem/findings:** macOS addition affected the shared Windows parser; cheap checks ran after expensive U2; upstream integration and evidence invalidation were late (F02, F05, F06, F10).
- **Evidence:** Turn `019fca50-fb77-7513-8465-40bbae9ef956`; `broker_drift`; current PR conflict.
- **Exact instruction / pseudodiff:**

```diff
+ When a later instruction adds or removes a platform, action catalog entry,
+ package class, runtime, schema, or delivery requirement, record an impact
+ slice before editing: changed requirements; shared contracts/catalogs;
+ dependent parsers/consumers; invalidated evidence; affected lanes; required
+ packaging/native gates; and branch-currency effect. Preserve unaffected
+ receipts. Run invalidated gates cheapest-to-expensive: canonical parsers and
+ rejection canaries, component checks, lifecycle suites, then one integration
+ suite on the frozen hash. Do not retitle or reframe the owning task around a
+ temporary slice.
```

- **Triggers:** Material late scope delta or shared contract hash change.
- **Exclusions:** Local implementation detail with no contract/evidence impact.
- **Model/orchestration implications:** Fast impact mapper; integration owner decides ordering.
- **Required artifact:** Impact/invalidation slice.
- **Guardrails:** Do not rerun unaffected gates; do not weaken required final integration or native proof.
- **Interactions/conflicts:** Narrows and tests current hash-aware cadence rather than duplicating it.
- **Expected effect:** 20–90 min per material delta; reliability high.
- **Effort:** Small-medium. **Confidence:** High. **Overfitting risk:** Low.
- **Acceptance criteria:** Adding one catalog ID immediately schedules all parsers before lifecycle; unaffected platform receipts remain valid; pre-PR branch currency is checked.
- **Evaluation scenarios:** E2 shared schema change; E5 late scope/recovery.

### SC-08 — Stable objective-level task title

- **Target:** `plugins/agent-utilities/references/task-titles.md` after material-focus rule.
- **Change:** Narrow title updates.
- **Exact instruction:**

```diff
+ Keep the title anchored to the owning objective. A temporary platform slice,
+ failing test, review finding, or current implementation unit is not a material
+ focus change unless the user narrowed the objective or it became the durable
+ resume boundary.
```

- **Trigger:** Workflow-owned title during multi-phase delivery.
- **Exclusion:** User gives exact title or truly narrows objective.
- **Effect:** Small navigation/recovery improvement. **Effort:** Small. **Priority:** P2. **Confidence:** High. **Overfitting risk:** Low.
- **Acceptance:** A cross-platform broker task remains cross-platform while macOS is the current slice.

## Scope categories

### Generally useful

SC-01 through SC-06 and SC-08 apply broadly when their explicit triggers fire.

### Task-class-specific

SC-07 is most valuable for cross-platform/shared-schema work and should remain trigger-based. SC-01 is especially important for plugins, native helpers, installers, and generated assets.

### Thread-only corrections

- The exact macOS/Homebrew action list belongs in this product plan, not Agent Utilities.
- The specific choice among PowerShell, C#, Rust, or C++/WinRT must not become a skill rule.
- The stale/mismatched thread ID should be corrected in handoff evidence, not hard-coded into workflow policy.
- The exact SDK `8.0.423`, Homebrew cask semantics, and WinGet provider design are repository concerns.

## Interactions and contradictions

- **SC-03 versus proactive delegation:** Delegate when a lane has a consumed independent output; do not delegate merely to fill slots.
- **SC-04 versus deep reasoning:** The budget requires a decision receipt, not immediate code. Strong-model architecture remains allowed.
- **SC-05 versus mandatory review:** Reduce duplicate reviewers, never the independent security/correctness gate.
- **SC-07 versus final verification:** Preserve unaffected evidence, but still run one required final integration and all native/release gates.
- **SC-01 versus source portability:** Do not commit generated binaries by default. Prove an authenticated package/release route instead.

## Explicitly rejected changes

1. **“Always use LFG instead of CE Work.”** Rejected. Historical Goal Driven Delivery correctly routed an implementation-ready, initially local-only plan to CE Work return-to-caller; later user authorization changed the shipping boundary.
2. **“Ban .NET or compiled helpers.”** Rejected as overfit. The defect was absent delivery closure, not the language. A compiled helper is acceptable with a proven package/sign/install path.
3. **“Use fewer security reviews regardless of risk.”** Rejected. Reviews found real P0/P1 defects. SC-05 removes duplicate purpose and provider stalls while preserving independent review.
4. **“Run the full suite after every edit.”** Rejected. It increases wall time and invalidates more evidence. Use hash/dependency-based gates plus one frozen integration run.
5. **“Require a large task manifest for every request.”** Rejected. SC-03/SC-06 trigger only for multi-lane, remote, or long-running work.
6. **“Encode macOS privileged support in delivery skills.”** Rejected. Product scope belongs to the plan; the skill should detect objective-plan mismatch.
7. **“Always use the strongest model.”** Rejected. Strong models belong on architecture/security/review; fast/economical models should own mapping and mechanical work.
8. **“Shorten or skip native canaries to gain speed.”** Rejected. The run’s core failure is inadequate terminal proof; speed must come from ordering and reuse.

## Top-five acceptance bundle

The top five are ready to implement when all of these hold:

1. A fixture task with an unshipped binary blocks in plan admission.
2. A cross-platform objective/plan exclusion mismatch blocks before edits.
3. A complex task emits a four-lane DAG and closes unused scouts at fan-in.
4. A nonproducing implementation lane redirects once without provider-policy drift.
5. Thermos receives line/artifact/package facts and catches the architectural delivery gap without adding a third duplicate reviewer.
